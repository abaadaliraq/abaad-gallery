5. الصلاحيات وحماية البيانات
RLS وFORCE RLS مفعّلان على الجداول العامة الأربعة. لا توجد سياسة تسمح بقراءة أو كتابة مباشرة؛ جرى سحب الامتيازات عن PUBLIC وanon وauthenticated وservice_role للجداول نفسها.
هذه سياسة منع افتراضي مقصودة: كل الوصول عبر RPC محددة، لا عبر from(table) المفتوحة للمتصفح.
الدوال العامة SECURITY INVOKER؛ التنفيذ المميز المحصور في abaad_private بدوال SECURITY DEFINER وsearch_path فارغ وأسماء جداول مؤهلة. سُحبت EXECUTE الافتراضية من PUBLIC وanon وغير المخولين لكل دالة جديدة.
booking_slots / booking_create / booking_notification: منح EXECUTE للخادم service_role فقط؛ لا تستدعيها واجهة المتصفح مباشرة، ولا تعيد قائمة حجوزات شخصية عامة.
booking_snapshot / booking_arrival / booking_events: جلسة موظف حية ونشطة ودور admin أو protocol وارتباط Protocol بالمعرض عبر protocol_exhibition_staff. Sales لا يستطيع تنفيذها أو قراءة الأشخاص.
booking_slot_save / booking_manage: Admin فقط داخل قاعدة البيانات وAPI. Protocol لا يعدّل المواعيد أو السعات ولا يلغي/ينقل الحجوزات؛ لا يوجد حذف حجوزات.
كل إجراءات الحفظ الحساسة تعيد فحص الدور على الخادم وداخل RPC، ولا تقبل actor_id من المتصفح.
إنشاء الحجز يثبت السعر والمصدر والتاريخ من الموعد المحفوظ؛ أسعار أو أعداد وصول مزورة في الطلب لا تؤثر على السجل.
GRANT الخاص بـData API مراجع صراحة للدوال، لا اعتماد على امتيازات تلقائية أو تجاوز RLS من المتصفح.

6. آلية الربط بين المشروعين
المتصفح في Booking -> POST /api/exhibition/bookings على نفس الموقع -> تحقق Origin وJSON والحجم والحقول والهاتف وhoneypot -> RPC booking_create من خادم Node فقط.
GET /api/exhibition/slots يعيد فقط المواعيد المفتوحة المستقبلية وعدد المقاعد المتبقية، دون أسماء أو هواتف.
القاعدة تستخدم advisory transaction lock لطابور المعرض وقفل صف الموعد؛ فحص السعة وزيادة المحجوز وإدخال الحجز والإشعار في معاملة واحدة.
الموعد ذو capacity=NULL أو المغلق لا يقبل الحجوزات. لا يمكن تقليل السعة إلى أقل من المقاعد المحجوزة. إغلاق الموعد يمنع الحجوزات الجديدة ويحافظ على حجوزاته القائمة.
Idempotency: request UUID واحد مع SHA256 للمدخلات. التكرار يعيد الحجز نفسه، وتغيير المدخلات مع المفتاح نفسه يُرفض. يحتفظ المتصفح بالطلب في sessionStorage لاستعادته بعد تحديث الصفحة، وبنسخة ثابتة عند تعذر معرفة نتيجة الحفظ.
الحماية من الإساءة: حد دائم 10 محاولات جديدة لكل IP مجزأ في الساعة، لا يعتمد ذاكرة سيرفر Vercel المؤقتة. يستخدم x-vercel-forwarded-for الموثوق على Vercel؛ في التطوير دلو محلي واحد. يجب مراجعة قواعد WAF عند التفعيل العام أو عند تغير وسيط الشبكة.
تذكرة QR تحتوي ABAAD-BOOKING: ورمز HMAC عشوائي ظاهرياً بطول 256 بت، بلا اسم أو هاتف. القاعدة تخزن SHA256 فقط. يبقى EX مرجعاً يدوياً سريعاً للبحث بالاسم/الهاتف أيضاً.
لا توجد واجهة عامة لاسترجاع بيانات الشخص بمعرف الحجز وحده. تأكيد الطلب يُعاد فقط عبر إعادة إرسال مفتاح الطلب الأصلي ومدخلاته المطابقة.
الردود الحساسة private,no-store؛ لا تُخزن أسماء الزوار في cache عامة.
صفحة التأكيد داخل تجربة الحجز تُظهر بيانات التذكرة بعد نجاح الحفظ فقط، مع QR وإمكانية طباعة/حفظ PDF من المتصفح. إن تعذر توليد صورة QR بعد الحفظ يبقى المرجع اليدوي صالحاً ولا يضيع الحجز.

7. EmailJS وWhatsApp
الزيارات الاعتيادية: إرسال المتصفح القديم وفتح WhatsApp بعد نجاحه بقي كما هو.
المعرض: الحفظ أولاً، ثم محاولة EmailJS REST من الخادم على نفس Service/Template المتاحين، مع متغيرات الاسم والهاتف والعدد والتاريخ والوقت العربي وsummary والسعر المجاني. فشل الإشعار لا يحذف الحجز أو يُفشل تذكرته.
زر إعادة محاولة الإشعار يعيد الطلب نفسه؛ لا ينشئ حجزاً إضافياً. هناك مهلة دقيقة بين المحاولات، وlease لخمس دقائق عند تعطل طلب الإرسال، وحد ثلاث محاولات.
EmailJS لا يوفر هنا ضمان exactly-once؛ انقطاع الرد بعد التسليم يمكن أن يؤدي إلى بريد مكرر عند إعادة المحاولة، لكنه لا يكرر الحجز أو يستهلك مقاعد جديدة. الواجهة تقول «لم يُؤكد الإشعار» ولا تدعي التسليم.
WhatsApp رابط واضح يفتح الرسالة الجاهزة وينتظر الزائر أن يضغط إرسال؛ لم أدّعِ إرسال رسالة آلياً ولم أرسل رسائل اختبار حقيقية.
يجب مراجعة قالب EmailJS وقبول طلبات الخادم وإعداد المفتاح الخاص إن كان الحساب يتطلبه. لم تُغيّر إعدادات حساب EmailJS.

8. التشريفات والإدارة وتسجيل الوصول

البحث الموحد ضمن قسم الحجوزات يجلب أسماء الدعوات وحجوزات الجمهور كنوعين مستقلين، ويبحث بالاسم والهاتف بصيغ عراقية/عربية ومرجع الحجز. لا دمج تلقائياً بسبب تطابق الاسم.
يمكن مسح QR بالكاميرا أو كتابة مرجع الحجز أو الهاتف/الاسم. المسح يجلب حالة القاعدة فقط؛ لا يسجل الدخول تلقائياً. يجب فتح السجل واختيار العدد وتأكيده.
3 أشخاص: يمكن تسجيل 3 دفعة واحدة، أو 2 ثم 1. تمنع القاعدة شخصاً إضافياً أو الوصول إلى حجز ملغى. لكل وصول UUID عملية يعيد النتيجة نفسها عند إعادة الإرسال.
Protocol لا يسجل لتاريخ مختلف عن يوم بغداد. Admin يستطيع استثناء التاريخ أو delta سالباً لتصحيح العدد بسبب إلزامي؛ كل إجراء مسجل منفصل بالموظف والوقت.
الإلغاء أو نقل الموعد للإدارة فقط وبسبب. لا إلغاء/نقل مع وجود وصول؛ يلزم تصحيح الوصول أولاً. الإلغاء يحرر العدد مرة واحدة، والنقل يتحقق من الموعد الجديد وينقل المقاعد ذرياً ويبقي رقم الحجز والـQR كما هما.
/admin/bookings يعرض الإجمالي والمؤكد والملغى والزوار المتوقعين والواصلين، الجدول والتفاصيل وسجل الوصول، وإضافة المواعيد وتحديد سعاتها وإغلاقها وتعديلها وحجز النقل.
الجرس متاح في التشريفات حتى أثناء عرض ضيوف الافتتاح، ويعرض آخر 20 حجزاً محدثاً بالاسم والتاريخ والوقت والعدد والحالة. القائمة العامة تحفظ الوصول لبقية الحجوزات بالبحث والصفحات.
البيانات تُجلب من القاعدة عند الفتح وكل 5 ثوانٍ أثناء ظهور الصفحة، وعند عودة الاتصال/التركيز. هذا تحديث دوري قريب من الفوري، وليس ادعاء اشتراك Realtime. عند الانقطاع أو خطأ الصلاحية تزال البيانات القديمة ولا يُعرض نجاح وصول محلي وهمي.

حد مهم: PGlite ينفذ عبر اتصال واحد؛ طلبات Promise المتزامنة فيه لا تثبت تزاحم اتصالات PostgreSQL مستقلة. القفل والمعاملة موجودان ومراجعان، لكن اختبار ضغط باتصالات مستقلة يبقى شرطاً قبل فتح الإنتاج.
لم أختبر جلسة Admin/Protocol حقيقية على المخطط الجديد، ولا مسح كاميرا هاتف فعلي عبر HTTPS، ولا تسليم EmailJS حقيقياً، لعدم اعتماد SQL/الإعدادات وعدم السماح بتغيير الإنتاج الآن. هذه خطوات قبول نهائي وليست اختبارات ناجحة مزعومة.
تشغيل الاختبارات الجديدة من gallery-org: npm run test:bookings:db وnpm run test:bookings:server. يفترض الاختبار الأخير مجلد booking المجاور أو BOOKING_PROJECT_PATH لمساره.

10. متغيرات البيئة والإعدادات قبل التفعيل
القالب الآمن في Booking: .env.exhibition.example. أضيف استثناء لهذا القالب فقط في .gitignore، وجميع ملفات .env الفعلية بقيت مستثناة.
داخل Booking .env.local للاختبار المعتمد ثم Vercel Environment Variables عند الموافقة على النشر:
EXHIBITION_SUPABASE_URL: عنوان المشروع pwlwelxnrrignapdsyiw فقط؛ الخادم يرفض مشروعاً مختلفاً.
EXHIBITION_SUPABASE_SERVICE_ROLE_KEY: مفتاح خادم server-only؛ لا NEXT_PUBLIC ولا تخزين في المتصفح أو المستودع.
EXHIBITION_BOOKING_SECRET: سر عشوائي مستقل >=32 محرفاً، ثابت بعد إطلاق التذاكر؛ تغييره يكسر استعادة الرموز بنفس طلباتها، لذلك يلزم تدبير تدوير صريح لاحقاً.
BOOKING_ORIGIN: origin الموقع المسموح دون slash أخير؛ يضبط مستقلاً لكل بيئة اختبار/إنتاج.
EMAILJS_SERVICE_ID / EMAILJS_TEMPLATE_ID / EMAILJS_PUBLIC_KEY: قيم الخادم أو fallback للأسماء NEXT_PUBLIC_EMAILJS_* الحالية للحفاظ على إعداداتها.
EMAILJS_PRIVATE_KEY: فقط إذا كانت إعدادات الحساب تتطلب تصريح الخادم؛ server-only دائماً.
لا يحتاج gallery-org مفتاح service_role جديداً؛ يستمر بعميل الموظف وRLS القائمين. لا حاجة لتغيير Authentication أو إنشاء حسابات.
قبل الفتح: اعتماد ملف SQL المحدد ونسخته/hash؛ تطبيقه على المشروع المحدد فقط بعد الموافقة؛ تأكيد GRANT/advisors/schema cache؛ ضبط المتغيرات سراً؛ يحدد المدير المواعيد والسعات ويفتحها؛ إجراء اختبار باتصالات مستقلة وجلسة Protocol/Admin حقيقيتين وعلى هاتف؛ مراجعة EmailJS/WAF؛ ثم موافقة منفصلة على نشر المشروعين. لا تُنشأ حجوزات وهمية بالإنتاج للاختبار.
إغلاق المواعيد قبل اكتمال هذه الخطوات مقصود. لا يتطلب انتهاء المعرض تغيير مفتاح يدوي؛ قواعد التاريخ تعيد الزيارة الاعتيادية تلقائياً، والحجوزات القديمة تبقى محفوظة.
