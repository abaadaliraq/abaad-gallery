النتيجة وحدود الجاهزية
اكتمل التنفيذ المحلي للوحة الإدارة فوق المشروع الحالي. لم يُنشأ مشروع جديد ولم تُبنَ واجهتا التشريفات أو المبيعات من الصفر.
لم أطبّق admin.sql على Supabase، ولم أعدّل بيانات الضيوف أو الحضور أو المبيعات أو الأدوار الفعلية أو إعدادات المصادقة، ولم أُنشئ حسابات تجريبية.
اختبارات الواجهة والكتابة استخدمت PostgreSQL محلياً معزولاً (PGlite) وموظفين وضيوفاً مصطنعين. لا تمثل جلسة Admin حقيقية في Supabase.

1. الواجهة والوظائف المكتملة محلياً
- Layout إدارة مستقل RTL، وSidebar يمين بعرض 208px وقابلة للطي إلى 72px. يظل اسم المدير وتسجيل الخروج متاحين. قائمة الهاتف نافذة جانبية تفتح بزر وتغلق عند التنقل، مع ضبط التركيز وتمرير الخلفية.
- /admin: مؤشرات التشريفات الأربعة، والمبيعات الأربعة، والموظفين، وآخر العمليات. لا رسوم بيانية ولا أرقام ثابتة في كود المنتج.
- تُقرأ مؤشرات التشريفات والمبيعات من RPC الحالية وجداول Supabase تحت صلاحية Admin وRLS. دليل الموظفين وأعدادهم ينتظر توفر RPC الجديدة المعتمدة.
- يتم التفريق بين صفر مؤكد، واستعلام فاشل، ووظيفة بانتظار SQL. الخطأ أو غياب الوظيفة يعرض رسالة وشرطة «—» بدلاً من صفر مضلل.
- /admin/guests: جدول إداري بصور مصغرة واسم ومنصب وتصنيف وأولوية ووصول ومراجعة وإجراءات. بحث بالاسم والمنصب والجهة، وفلاتر التصنيف والأولوية والحضور والمراجعة.
- «بانتظار المراجعة» يعرض عدداً دقيقاً مستقلاً عن صفحة النتائج. فلتر المراجعة يشمل جميع الصفحات المحملة، وليس أول 24 سجلاً فقط.
- إضافة الضيف وتعديله يعيدان استخدام RPC الموجودة. الإضافة تستخدم protocol_merge_import لسجل واحد داخل قفل الاستيراد الحالي، وبهوية مصدر فارغة؛ بذلك لا تكرر سجلاً مستورداً ولا تتبنى أو تحدث هوية CSV بالخطأ. التكرار يعرض رفضاً واضحاً.
- التعديل يستخدم protocol_save_guest الحالية. لا يقبل حقول الوصول من المدخلات، ولا يغير معرف الدعوة. تبقى علامة مراجعة قائمة محفوظة عند تعديل البيانات بدلاً من رفعها من نموذج التعديل.
- اختيار المعرض يأتي من Supabase؛ إذا كان واحداً يُحدد تلقائياً وتظهر هويته داخل النموذج. لا معرفات معارض ثابتة داخل Components.
- المراجعة تعرض البيانات الحالية وسبب المراجعة ومصدرها. فتح السجل لا يعتمد البيانات. الاعتماد يتطلب إقراراً صريحاً ثم حفظاً مؤكداً، ويظل معطلاً حتى توفر RPC المعتمدة.
- /admin/staff: جدول الاسم والبريد والدور وحالة الوصول إلى التطبيق والمعارض وتاريخ سجل الموظف. البحث والفلترة والنموذج جاهزة مع التعطيل الواضح عند غياب SQL.
- إضافة موظف جديد غير مفعّلة؛ لم يُضف Auth Admin secret أو Service Role Key. البريد للقراءة فقط، والتفعيل المقصود هو staff_roles.is_active، ولا يغيّر إعدادات Supabase Auth أو كلمات المرور.
- /admin/activity: أحداث الوصول والتراجع، وحالات الأعمال الفعلية من الجداول الحالية، مع فلاتر القسم والنوع والتاريخ والموظف. وقت العرض هو created_at للحدث، وليس وقت تحديث الصفحة. التاريخ وفق توقيت بغداد.
- /admin/settings: الاسم والجهة والموقع والهوية من Config الحالية للقراءة فقط؛ حالة المعرض من Supabase حين تتيح السياسات قراءتها. لا زر حفظ ولا مصدر إعدادات جديد منافس.
- /admin/artworks: ملخص الفنانين وعدد الأعمال وحالتها للقراءة فقط. لا أعمال أو أسعار أو صور مضافة. احتُفظ بمكونات الإدخال السابقة دون توسيعها.
- /admin/artworks/preview: عرض إداري محمي يعيد استخدام معرض المبيعات للقراءة فقط؛ لا حجز أو بيع أو تعديل عبر هذا العرض، ولا تحويل دور Admin إلى Sales.

2. ما يحتاج SQL للموافقة
الملف: supabase/admin.sql، ونسخة التسليم phase05-admin-review.sql.
SHA256: e785c69628a00e90e7acffbef101e7d073c095dc1204e4f10c3a016cd7d44e46
الملف يعرّف ثلاث RPC عامة بأغلفة SECURITY INVOKER، ومنطقاً محدوداً داخل abaad_private:
- admin_staff_directory: قراءة دليل الموظفين والبريد من Auth إلى مدير نشط ذي جلسة حية، مع الأعداد والمعارض وقدرات الواجهة.
- admin_update_staff: تعديل الاسم والدور وتفعيل الوصول وربط المعارض. يتحقق من النسخة، ويقفل التعديلات الإدارية تسلسلياً، ويرفض تغيير المستخدم لدوره أو تعطيل نفسه، ويحمي آخر Admin نشط.
- admin_approve_guest: اعتماد صريح مع فحص توقيتي تعديل الضيف والدعوة تحت قفل الصفوف. يغيّر review_required فقط مع updated_at؛ لا يغيّر الأولوية أو المصدر أو بيانات الوصول.
لا ينشئ الملف جداول أو حسابات أو أحداثاً، ولا يغيّر سياسات RLS أو صلاحيات الكتابة المباشرة إلى staff_roles. نشر تعريفاته لا يعدل صفوفاً حالية؛ التعديلات المستقبلية تتم فقط عند استدعاء إداري صريح.
وظائف SECURITY DEFINER داخل مخطط خاص، مع search_path فارغ وصلاحيات EXECUTE مقيدة وفحص الهوية والدور والجلسة داخل قاعدة البيانات. لا اعتماد على user_metadata ولا مفاتيح سرية جديدة.

4. حماية لوحة الإدارة
كل صفحات /admin والصفحات الفرعية تتحقق من Admin النشط والجلسة على الخادم. لا يُعتمد على Layout المخزن بين التنقلات وحده؛ الصفحات وواجهات API وServer Actions تتحقق أيضاً.
عمليات API تحفظ تجديد كوكيز الجلسة وفق النمط الحالي، ثم تعيد فحص الدور. الاستجابات private/no-store.
تُرفض Protocol وSales قبل قراءة بيانات الإدارة. الصلاحيات الجديدة للموظفين محصورة في RPC بعد الاعتماد؛ لا محاولة للكتابة المباشرة إلى staff_roles أو فتحه للمستخدمين.
فحص HTTP دون جلسة على localhost:3000 أكد حراسة الصفحات الست وثلاث واجهات API، مع إعادة التوجيه إلى تسجيل الدخول. قد يكون HTTP 200 للقشرة المتدفقة في Next.js؛ جرى التحقق من تحويل الجلسة داخل الاستجابة ولم يُعدّ 200 وحده نجاح وصول.
